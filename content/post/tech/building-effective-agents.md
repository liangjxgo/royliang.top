## 引言

过去一年里，我们与数十个来自不同行业的团队合作构建大语言模型（LLM）智能体。一个反复出现的规律是：最成功的实现往往**并不依赖**复杂框架或专用库。相反，它们都是用简单、可组合的模式搭建起来的。

在这篇文章里，我们分享从客户合作和自研智能体过程中积累的经验，为开发者构建有效智能体提供实用建议。

## 什么是智能体？

"智能体"（Agent）有多种定义方式。一些客户把智能体定义为完全自主的系统——能在较长时间内独立运行，调用各种工具来完成复杂任务；另一些人则用这个词描述更"规定式"的实现，即沿着预设工作流执行的程序。在 Anthropic，我们把所有这些变体统称为 **agentic systems（智能体系统）**，但在架构上我们刻意区分 **工作流（workflows）** 与 **智能体（agents）**：

- **工作流**：LLM 和工具被通过**预定义的代码路径**编排起来的系统。
- **智能体**：LLM **动态地主导自己的流程和工具使用**，对如何完成任务保持控制权的系统。

下文我们将详细探讨这两类智能体系统。在附录 1（"智能体在实践中的应用"）中，我们描述了客户已发现的两类特别有价值的应用领域。

## 何时使用（以及何时不使用）智能体

在用 LLM 构建应用时，我们的建议是：**先寻找可能的最简方案**，只在确有必要时才增加复杂度。这意味着有时候你根本不应该构建智能体系统。智能体系统往往是用**更高的延迟和成本**换取**更好的任务表现**，你需要判断这种权衡是否值得。

当确实需要更多复杂度时：

- **工作流**适合定义清晰、需要可预测性和一致性的任务；
- **智能体**适合需要灵活性和模型驱动决策、并要在规模化场景下执行的任务。

但对很多应用来说，**用检索和上下文示例优化单次 LLM 调用就足够了**。

## 何时以及如何使用框架

市面上有很多框架能让智能体系统更易实现，例如：

- **Claude Agent SDK**；
- AWS 的 **Strands Agents SDK**；
- **Rivet**，一个拖拽式 LLM 工作流构建器；
- **Vellum**，另一个用于构建和测试复杂工作流的图形化工具。

这些框架让入门变得容易——它们简化了诸如调用 LLM、定义并解析工具、把多次调用串联起来这类标准底层任务。然而，它们往往会引入额外的抽象层，**掩盖底层的 prompt 与响应**，使调试更困难；也容易诱导你添加本不需要的复杂度。

我们建议开发者**从直接调用 LLM API 开始**：很多模式几行代码就能实现。如果你确实要使用框架，务必理解其底层代码。对"底层到底在做什么"持有错误假设，是客户报错最常见的来源之一。

参见我们的 cookbook 获取示例实现。

## 基础构件、工作流与智能体

在本节中，我们将探索我们在生产环境中见到的智能体系统常见模式。从最基础的构建块——**增强型 LLM（augmented LLM）**开始，逐步增加复杂度，从简单的组合式工作流走向自主智能体。

### 基础构件：增强型 LLM

智能体系统的基本构建块是一个经过增强的 LLM——它配备了**检索（retrieval）**、**工具（tools）**、**记忆（memory）**等能力。我们当前的模型可以主动使用这些能力：自行生成搜索查询、选择合适工具、并决定哪些信息需要保留。

```
       ┌──────────────────────────┐
       │     增强型 LLM            │
       │  检索 · 工具 · 记忆        │
       │   围绕一次模型调用        │
       └──────────────────────────┘
```

我们建议在实现时聚焦两个关键点：**一是**针对你的具体场景定制这些能力，**二是**为 LLM 提供简单、文档完善的接口。实现增强的方式有很多，其中一种是通过我们最近发布的 **Model Context Protocol**——开发者只需简单的客户端实现就能集成不断壮大的第三方工具生态。

本文余下部分，我们**假设每次 LLM 调用都能访问到这些增强能力**。

### 工作流：提示链（Prompt Chaining）

提示链将任务拆解成一连串步骤，每个 LLM 调用都处理上一步的输出。你可以在任意中间步骤加入**程序化检查**（即下文示意图中的"gate"），以确保流程仍然在正轨上。

```
LLM → [gate 门控检查] → LLM → [gate] → LLM   （串行管线）
```

**何时使用：**当任务可以被干净地分解为若干固定的子任务时非常理想。核心目标是**用延迟换取更高精度**——让每次 LLM 调用都更容易完成。

**典型应用：**

- 先生成营销文案，再翻译成另一种语言。
- 先写一份文档的大纲，校验大纲是否符合某些标准，再基于大纲撰写正文。

### 工作流：路由（Routing）

路由对输入进行分类，并把它导向一个专门的后续处理任务。这种工作流可以实现**关注点分离**，并构建更专门的 prompt。如果没有这种模式，对某一类输入做优化可能会损害其他输入上的表现。

```
            ┌──▶ 专门流程 A
分类器 ─────┼──▶ 专门流程 B
            └──▶ 专门流程 C
```

**何时使用：**路由适合**存在清晰类别、可分别处理**的复杂任务，且分类可以准确完成（无论是用 LLM 还是用更传统的分类模型/算法）。

**典型应用：**

- 把不同类型的客服查询（一般问题、退款请求、技术支持）路由到不同的下游流程、prompt 和工具。
- 把简单/常见问题路由到更小、更具成本效益的模型（如 Claude Haiku 4.5），把困难/异常问题路由到更强的模型（如 Claude Sonnet 4.5），以此优化整体表现。

### 工作流：并行化（Parallelization）

LLM 有时可以**同时**处理一个任务，然后把它们的输出通过程序聚合起来。并行化有两种关键变体：

- **分段（Sectioning）**：把任务拆为可并行执行的独立子任务。
- **投票（Voting）**：对同一任务运行多次，以获得多样化的输出。

```
分段：  一个 LLM ──┬──▶ 子任务 1 ──┐
                  ├──▶ 子任务 2 ──┼──▶ 聚合
                  └──▶ 子任务 3 ──┘

投票：  同一 LLM ×N 次 ──▶ 投票 / 择优
```

**何时使用：**当拆分后的子任务可以并行以加速、或需要多视角/多次尝试来提高结果置信度时，并行化很有效。对涉及多个考量维度的复杂任务，**把每个维度交给一次单独的 LLM 调用**通常表现更好——每个调用可以专注于具体方面。

**典型应用：**

- **分段**：实现护栏（guardrails）时，让一个模型实例处理用户查询，另一个模型实例检查是否有不当内容或请求。这比让同一个 LLM 调用既管护栏又管核心回答效果更好。
- 对 LLM 性能做自动化评测（evals）：每次 LLM 调用评估模型在给定 prompt 上某一维度的表现。
- **投票**：审查一段代码是否有漏洞，多个不同的 prompt 各自审查并标记问题。
- 评估一段内容是否违规，用多个 prompt 各自评估不同方面，或要求不同的投票阈值，以平衡误报与漏报。

### 工作流：编排者-执行者（Orchestrator-Workers）

在编排者-执行者工作流中，一个中心 LLM **动态地**拆解任务、委派给若干 worker LLM，并综合它们的结果。

```
                ┌──▶ Worker 1 ──┐
Orchestrator ───┼──▶ Worker 2 ──┼──▶ 综合结果
                └──▶ Worker 3 ──┘
        （任务由编排者动态分配）
```

**何时使用：**适合**无法预先确定需要哪些子任务**的复杂工作（例如编码任务里，需要修改几个文件、每个文件做何种修改，往往取决于任务本身）。虽然它与并行化在拓扑结构上类似，但**关键区别在于灵活性**——子任务不是预先定义的，而是由编排者基于具体输入动态决定。

**典型应用：**

- 对多个文件做复杂修改的编码产品。
- 需要从多个来源收集并分析信息的搜索类任务。

### 工作流：评估者-优化者（Evaluator-Optimizer）

在评估者-优化者工作流中，一个 LLM 调用生成响应，另一个 LLM 在一个循环里提供评估与反馈。

```
       ┌──────────────────────────┐
       ▼                          │
  生成器 LLM ──▶ 评估器 LLM ──▶ 反馈
       │
       └──▶ 满足标准则输出
```

**何时使用：**当**有明确的评估标准**、且**迭代式精修能带来可衡量的价值**时特别有效。两个适用信号是：第一，当人类明确表达反馈时，LLM 的响应可以被显著改进；第二，LLM 自身能够提供此类反馈。这与人类作家在打磨文档时所经历的迭代写作过程类似。

**典型应用：**

- 文学翻译：翻译 LLM 可能一开始捕捉不到的微妙之处，但评估 LLM 能给出有用的批评。
- 复杂的搜索任务：需要多轮搜索和分析才能收集到全面信息，由评估者判断是否还需要继续搜索。

### 智能体：自主智能体

随着 LLM 在关键能力上逐渐成熟——理解复杂输入、进行推理与规划、可靠地使用工具、从错误中恢复——智能体正在生产环境中涌现出来。智能体的工作起点要么是来自人类用户的命令，要么是与人类的交互式讨论。**任务一旦清晰，智能体就会独立地规划并执行**，可能在过程中回头向人类请求更多信息或判断。在执行过程中，智能体必须在每一步从环境中获得"地面真相"（ground truth，比如工具调用结果或代码执行结果）来评估自身进度，这至关重要。智能体可以在检查点或遇到阻碍时暂停，请求人类反馈。任务通常在完成时终止，但加入停止条件（比如最大迭代次数）以保持控制也很常见。

```
          ┌────────────────────────┐
          ▼                        │
  任务 → 思考 + 工具调用 + 观察 ───┘  ──▶ 完成 / 达到停止条件
                 │
                 └──▶ 人类可介入
```

智能体可以处理复杂任务，但其实现往往很朴素：通常**只是 LLM 在一个循环里基于环境反馈使用工具**。因此，**把工具集及其文档设计得清晰、周到至关重要**。我们在附录 2（"为工具做提示工程"）中展开工具开发最佳实践。

**何时使用：**智能体适合**开放式问题**——难以或无法预测所需的步骤数、无法硬编码一条固定路径。LLM 可能会运行很多轮，你必须对它的决策能力有一定信任。智能体的自主性使其非常适合在**受信任环境**中规模化任务。

智能体的自主性也意味着**更高的成本**和**错误累积的可能性**。我们建议在沙箱环境中做广泛测试，并配置合适的护栏。

**典型应用**（以下示例来自我们的自研实现）：

- 一个能解决 SWE-bench 任务的编码智能体——这类任务需要根据任务描述编辑多个文件；
- 我们的"computer use"参考实现——Claude 使用计算机来完成任务。

```
任务描述 → 探索代码 → 编辑 → 运行测试 → 修复 → 完成
        （编码智能体的高层流程）
```

## 组合与定制这些模式

这些构建块不是硬性规定。它们是开发者可以根据不同场景**塑造和组合**的常见模式。和任何 LLM 特性一样，成功的关键在于**度量表现并迭代实现**。再说一遍：只有当复杂度能**切实改善结果**时，才去增加它。

## 总结

在 LLM 领域取得成功，不是靠构建最复杂的系统，而是**构建适合自己需求的正确系统**。先从简单的 prompt 开始，通过全面的评测来优化它们；只有当简单方案不够用时，才引入多步的智能体系统。

实现智能体时，我们遵循三条核心原则：

> 1. **保持设计简洁。**
> 2. **显式地展示智能体的规划步骤**，把透明度放在首位。
> 3. **精心打磨 agent-computer interface（ACI）**——通过充分的工具文档和测试。

框架能帮你快速起步，但在走向生产时，不要犹豫去**减少抽象层、用基础组件来构建**。遵循这些原则，你就能打造出不仅强大、而且可靠、可维护、被用户所信任的智能体。

## 附录 1：智能体在实践中的应用

在与客户合作中，我们发现了两类特别有前景的 AI 智能体应用，它们很好地展示了上文讨论的模式的实用价值。两类应用都说明：当任务**既需要对话又需要行动**、有清晰的**成功标准**、能形成**反馈回路**，并嵌入**有意义的人类监督**时，智能体带来的价值最大。

### A. 客户支持

客户支持把熟悉的聊天机器人界面与通过工具集成带来的增强能力结合在一起。这对更开放式的智能体来说是个天然契合的场景，因为：

- 支持类交互自然沿着**对话流**展开，同时需要访问外部信息和执行动作；
- 可以集成工具来拉取客户数据、订单历史和知识库文章；
- 退款发放、工单更新等动作可以通过程序化方式处理；
- 成功与否**可以通过用户定义的解决方案来清晰度量**。

已有几家公司通过"按成功解决收费"的**按用量计费**模式证明了这种方法的可行性——这本身就是对自家智能体有效性的信心体现。

### B. 编码智能体

软件开发领域已经展现出 LLM 特性的显著潜力，能力从代码补全一路演进到自主问题解决。智能体在此场景下尤其有效，因为：

- 代码方案**可以通过自动化测试验证**；
- 智能体可以用测试结果作为反馈来迭代方案；
- 问题空间是**定义良好且结构化**的；
- 输出质量可以客观度量。

在我们自己的实现中，智能体已经能在 SWE-bench Verified 基准上**仅凭 pull request 描述就解决真实的 GitHub issue**。但请注意：虽然自动化测试能帮助验证功能，**人类评审仍然至关重要**，以确保方案与更广泛的系统需求保持一致。

## 附录 2：为工具做提示工程

无论你在构建哪种智能体系统，**工具**都很可能是其中重要的一部分。工具让 Claude 能够通过在 API 中明确指定结构来与外部服务和 API 交互。当 Claude 决定调用工具时，它会在响应里返回一个 tool use 块。**工具的定义和规范，理应和你整体的 prompt 一样获得充分的提示工程关注**。本附录简要介绍如何为工具做提示工程。

同一种动作往往有多种方式可以描述。比如，描述一次文件编辑可以写 diff，也可以重写整个文件；结构化输出可以把代码放在 markdown 里，也可以放在 JSON 里。在软件工程意义上，这些差异是"装饰性"的，可以无损地互相转换。但**对 LLM 而言，有些格式比另一些难写得多**。写 diff 需要在写新代码之前就知道 chunk header 里要改变多少行；把代码写在 JSON 里（相较 markdown）需要额外转义换行和引号。

关于工具格式的选择，我们建议：

- 给模型**足够的 token 去"思考"**，不要让它把自己逼到死角。
- 让格式尽量**接近模型在互联网上自然见过的文本**。
- 确保没有格式"开销"——比如要求精确数几千行代码，或对写出的代码做字符串转义。

一个经验法则：想想人们花多少精力打磨 **人机接口（HCI）**，然后**准备好把同样的精力投入到 agent-computer interface（ACI）上**。以下是一些具体建议：

- **把自己放到模型的位置上**：仅凭描述和参数，这个工具的用法是否一目了然？如果你需要仔细思考，那模型大概也需要。一个好的工具定义通常包含**示例用法、边界情况、输入格式要求、与其他工具的清晰边界**。
- **如何通过调整参数名或描述让事情更明显**？把这看作是给团队里一个初级开发者写优秀的 docstring。当你有很多相似的工具时，这一点尤其重要。
- **测试模型如何使用你的工具**：在我们的 workbench 里跑大量示例输入，观察模型会犯哪些错，然后迭代。
- **给工具做 poka-yoke（防呆设计）**：调整参数，让犯错的代价更高、更不容易发生。

> 在为 SWE-bench 构建智能体的过程中，**我们花在优化工具上的时间，其实比花在整体 prompt 上的时间还多**。例如我们发现：当智能体离开根目录之后，使用相对路径的工具很容易出错。为了解决这个问题，我们把工具改成**始终要求绝对路径**——之后模型在这个方法上就再没出过错。
